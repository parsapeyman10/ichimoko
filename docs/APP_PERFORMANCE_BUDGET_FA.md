# کنترل حجم، پردازش و جلوگیری از کرش — معماری نسخهٔ ۳.۹.۲۹

هدف این سند: برنامه روی گوشی‌های ضعیف هم پایدار بماند — بدون کرش حافظه، بدون لگ، و بدون رشد
بی‌پایان حجم داده. هر مورد دو بخش دارد: **آنچه در همین نسخه پیاده شد** و **آنچه گام بعدی است**.

---

## ۱. آنچه در ۳.۹.۲۹ پیاده شد

### ۱.۱. هم‌گراسازی انتشار وضعیت (State coalescing)

مشکل: هر تیک قیمت یک `StateFlow` را عوض می‌کرد و کل صفحه (کارت استراتژی، کارنامه، لیست) دوباره
ساخته می‌شد.

راه‌حل: `core/UiUpdateCoalescer.kt` — حداکثر ۴ انتشار در ثانیه برای هر کلید (۲۵۰ms). منطق معاملاتی
روی **هر** تیک اجرا می‌شود (`latestTicks`)، اما UI با نرخ محدود به‌روز می‌شود.

```kotlin
latestTicks[symbol] = tick                 // همیشه
if (uiCoalescer.shouldPublish("tick:$symbol", tick.at)) {
    _liveTicks.value = _liveTicks.value + (symbol to tick)   // حداکثر ۴/ثانیه
}
```

### ۱.۲. فرماندار منابع (Memory-aware budget)

مشکل: تعداد رکوردهای آرشیو و تعداد رندر هم‌زمان تصویر، اعداد ثابتِ کدشده بودند؛ روی گوشی با
heap ۱۲۸–۱۹۲ مگابایت همین ترکیب باعث `OutOfMemoryError` می‌شد.

راه‌حل: `core/AppResourceGovernor.kt` بودجه را از `Runtime.maxMemory()` می‌سازد:

| heap دستگاه | بودجهٔ آرشیو | سقف رکورد | رندر هم‌زمان | مقیاس بوم |
|---|---|---|---|---|
| ۱۲۸MB | ۱۲MB | ۲۵۶ | ۱ | ۰.۶۲ |
| ۱۹۲MB | ۱۲MB | ۳۸۴ | ۱ | ۰.۷۸ |
| ۲۵۶MB | ۱۵MB | ۵۱۲ | ۲ | ۰.۹۰ |
| ۵۱۲MB | ۳۰MB | ۸۰۰ | ۲ | ۱.۰۰ |

`TradeSnapshotArchiveManager.pruneToBudget()` در هر شروع برنامه قدیمی‌ترین تصاویر را حذف می‌کند تا
حجم آرشیو از بودجه رد نشود (پاک‌سازی هم فایل و هم ردیف ایندکس).

### ۱.۳. قفل رندر تصویر

ساخت هر اسکرین‌شات یک `Bitmap` چند مگابایتی می‌خواهد. سه مسیر هم‌زمان (گالری، ثبت خودکار، خروجی PDF)
می‌توانستند هم‌پوشانی کنند. اکنون رندرها با `renderLock` سریالی می‌شوند.

### ۱.۴. کوتاه‌کردن صفحهٔ ژورنال

صفحهٔ ژورنال پیش از این یک `Column` بسیار بلند با ده‌ها ردیف عدد و نوار ابزار افقی بود. اکنون:

- کارنامه در ۴ تب کوتاه (خلاصه / ریسک / تفکیک / توزیع R) با `AnimatedVisibility`؛
- شبکهٔ ۲×۲ به‌جای ردیف‌های چهارستونی (متن فارسی نمی‌شکند)؛
- ابزارهای خروجی در یک کارت تاشو (پیش‌فرض بسته)؛
- همهٔ `Text`ها `maxLines` + `ellipsis` دارند.

کمتر ساخته‌شدن = کمتر جابه‌جایی حافظه و کمتر jank در اسکرول.

### ۱.۵. سقف حافظهٔ یادگیری

`SessionExitLearning.MAX_OBSERVATIONS = 480` و `SessionExitLearningStore` حداکثر ۶۰ «خروج معلق»
نگه می‌دارد؛ قدیمی‌ترها حذف می‌شوند. فایل وضعیت هم هر بار کامل بازنویسی می‌شود (بدون رشد).

## ۲. گام‌های بعدی پیشنهادی (روش‌های روز دنیا)

اینها اندازه‌گیری و بهینه‌سازی‌های بعدی هستند، به ترتیب بیشترین سود:

1. **Baseline Profiles + Macrobenchmark** — پر شدن اولیهٔ Compose و لیست‌ها را ۲۰–۴۰٪ سریع‌تر
   می‌کند. نیاز به ماژول `baselineprofile` و یک دستگاه/امولاتور در CI دارد.
2. **R8 Full Mode + shrinkResources** — در `release` فعلاً `isMinifyEnabled = false` است. با قواعد
   `kotlinx.serialization` میتوان حجم APK را ۲۰–۳۰٪ کم کرد؛ پیش‌نیاز: تست دودی روی سریال‌سازی.
3. **Paging 3 برای ژورنال** — با ۴۷۰+ معامله، لیست باید صفحه‌بندی و `LazyColumn` با `key` شود تا
   فقط آیتم‌های دیده‌شده ساخته شوند.
4. **Compose stability** — مدل‌های `PaperTrade` و رکوردهای آرشیو `@Immutable` شوند و لیست‌ها از
   `kotlinx.collections.immutable` استفاده کنند تا skip شدن Composables بیشتر شود.
5. **StrictMode + LeakCanary در debug** — کشف I/O روی main و نشتی Context (سرویس‌ها، Bitmapها).
6. **JankStats** — ثبت فریم‌های کند در همان گوشی کاربر و ارسال خلاصه در خروجی PDF عیب‌یابی.
7. **WorkManager برای کارهای دوره‌ای** — آرشیو، بکاپ روزانه و خلاصه‌سازی آمار به‌جای اجرا در حلقهٔ UI.
8. **سقف حافظهٔ کش کندل** — `LiveQuoteFetcher` باید LRU با سقف مگابایتی داشته باشد (۱۵ نماد ×
   دو تایم‌فریم).

## ۳. بودجه‌های هدف

| سنجه | هدف |
|---|---|
| حافظهٔ پایه پس از باز شدن ژورنال | < ۱۲۰MB روی دستگاه ۱۹۲MB |
| حداکثر jank در اسکرول ژورنال | < ۵٪ فریم‌های کند |
| زمان باز شدن صفحهٔ ژورنال | < ۶۰۰ms |
| حجم آرشیو تصویری | ≤ بودجهٔ فرماندار (۱۲–۹۶MB) |
| رکورد آرشیو در حافظه | ≤ ۸۰۰ |
| نشر وضعیت UI | ≤ ۴ در ثانیه برای هر نماد |

## ۴. تست‌ها

`SessionExitTimingTest` شامل آزمون‌های `UiUpdateCoalescer` و `AppResourceGovernor` است:
نرخ انتشار (اولین بله، سپس نه، پس از بازه بله)، یکنوایی بودجه با حافظه، سقف رکورد و احترام به بودجهٔ
بایت. این تست‌ها بدون شبیه‌ساز و روی JVM اجرا می‌شوند.
